אשף Google ב־Node — הכנה והפעלה מבוקרת

זהו תוסף נפרד לכניסה המקומית, ולא אישור שחיבור Google חי כבר נבדק. מסמך docs/local-auth.txt מתאר את התקנת הבסיס המקומי; ההוראות כאן מוסיפות מעליו ניהול Client ID מאומת בלוח. אין להפעיל או לבטל שיטת כניסה רק על סמך הצלחת בדיקות בענן.

1. גבולות ההתקנה

האפשרות CMS_GOOGLE_SETUP_ENABLED=false כברירת מחדל. הפעלתה דורשת CMS_LOCAL_AUTH_ENABLED=true וחשבון בעל הרשאה מקומי שכבר הוקם ונבדק. ה־Worker הישן, OWNERS והרשאות עורכי Google נשמרים. אין יצירת חשבון, הענקת תפקיד או קישור זהות אוטומטי מתוך אשף Google.

שומרים CMS_STAGING=true, CMS_READ_ONLY=true ו־CMS_PUBLISH_ENABLED=false לאורך בדיקת ההתחברות. שינויי אישורי התחברות מותרים; שינויי תוכן ופרסום נשארים חסומים. אין ייבוא נתונים חוזר, שינוי DNS או העברת כותב כחלק מהתוסף.

מתקינים יחד app וקובצי admin שנבנו מאותו קומיט מאושר, עם package.json ו־package-lock.json התואמים. התלות jose בגרסה המדויקת 6.2.14 היא תלות ייצור; אין להשמיט אותה יחד עם devDependencies. משתמשים ב־Node 24 ומעלה וב־Run NPM Install עם omit=dev, ignore-scripts=true והתצורה הפרטית שנבדקה. שומרים את ה־runtime הקודם ואת גיבויי הקבצים, המסד והגדרות האחסון; מאמתים מניפסט, קוד יציאה וטעינת התלות לפני הפעלה.

2. הוספת סכימה ללא Terminal

משאירים CMS_GOOGLE_SETUP_ENABLED=false עד השלמת ההכנה. מגבים את המסד הקיים, כולל טבלאות auth. תוכנית ללא חיבור למסד או קריאת סודות:

node scripts/setup-google-auth.mjs

אותה תוכנית זמינה כ־npm run cms:auth:google:setup. משווים את schemaSha256 שבדוח לסכימה שבחבילה המאושרת. לאחר מכן מריצים פעם אחת:

node scripts/setup-google-auth.mjs --apply --database yoterber_heichal_preview --schema-sha256 REVIEWED_GOOGLE_SCHEMA_SHA256

MYSQL_DATABASE בתצורה חייב להיות זהה ליעד. הכלי מאמת את סכימת היישום וה־auth הקיימת, ומוסיף רק google_auth_config עם רשומת תצורה ריקה. הוא אינו משנה טבלאות קיימות, יוצר סיסמה או מפעיל Google. מצפים ל־exit 0, schemaInitialized=true ו־verified=true. טבלה קיימת או סכימה חלקית מחייבות בדיקה פרטית, לא מחיקה או הרצה חוזרת עיוורת; DDL ב־MySQL אינו מתבטל אוטומטית בכשל.

אפשר להריץ את התוכנית דרך Run JS Script. אם הממשק אינו מעביר ארגומנטים, משתמשים בדפוס Cron חד־פעמי שב־docs/local-auth.txt: Node מוחלט מאומת, קובץ פקודות פרטי, runtime.env תואם בהרשאות 0600, umask 077, נעילה, לוג פרטי וקוד יציאה. מחליפים את נתיב הסקריפט ואת גיבוב הסכימה בדוגמה, ומשתמשים בשמות נעילה ולוג חדשים. אין סודות בשורת Cron או בפלט. לאחר הריצה מסירים את המשימה ומאמתים שרשימת Cron ריקה.

3. דגלים ומקור ה־Client ID

אחרי הסכימה מפעיל האחסון מגדיר CMS_GOOGLE_SETUP_ENABLED=true לצד CMS_LOCAL_AUTH_ENABLED=true. CMS_GOOGLE_AUTH_ENABLED נשאר מתג שליטה ברמת האחסון: false מונע הפעלה גם לאחר הכנה והוכחת זהות. אפשר להכין ולבדוק את המועמד כשהמתג כבוי; להפעלה מלאה המפעיל צריך להגדיר אותו true ולהפעיל מחדש באופן מבוקר.

גם כאשר המתג true, רשומת תצורה חדשה ללא active_client_id אינה מאפשרת כניסת Google רגילה. הכניסה תופעל רק לאחר אימות והפעלה מפורשים באשף. הכניסה המקומית נשארת פעילה בכל השלבים.

במצב מנוהל GOOGLE_CLIENT_ID מהסביבה אינו מקור ההגדרה. השרת והדפדפן מקבלים את מזהה הלקוח הפעיל מאותה רשומת MySQL; /auth/options מחזיר googleManaged=true ואת googleClientId הפעיל רק כשהשיטה מופעלת. הלקוח הסטטי הישן אינו נבחר כתחליף. תצורת ה־Worker הישן נשארת כפי שהייתה. googleAvailable/activationAllowed משקפים הרשאת הפעלה בתצורת השרת, לא הצלחת בדיקת Google חיה.

4. ההגדרה ב־Google Cloud

בעל ההרשאה נכנס מקומית ובוחר בלשונית הגדרות התחברות את אשף Google. אפשר להשתמש בפרויקט Google Cloud קיים או ליצור חדש בחשבון שיש אליו גישה והרשאה מתאימה. יצירת הפרויקט ורישום OAuth מבוצעים במסוף Google, לא אוטומטית מתוך האתר:

https://console.cloud.google.com/auth/clients
https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid

אפשר לקצר את שלב המסוף באמצעות סוכן הדפדפן המחובר של המשתמש: לפתוח את הפרויקט הנבחר, למלא שם יישום והמקור שמופיע באשף, ולאסוף את ה־Client ID הציבורי בחזרה לאשף. הסוכן משתמש בממשק Google המאושר; אין צורך לתת לאתר גישת IAM או להעביר אליו סיסמת Google, cookies של המסוף או Client secret. בחירת חשבון/פרויקט עמומה, כניסה לחשבון ואישורים הנדרשים מהמשתמש נשארים בידיו. האתר עצמו אינו שולט בלשונית Google ממקור אחר.

Google מציינת שיצירה ושינוי של לקוח OAuth רגיל אינם נתמכים באופן תכנותי, ודורשים את Cloud Console. לכן האשף אינו מציג יצירת פרויקט אוטומטית או משתמש ב־API פרטי של המסוף. מסלולי IAP או Workforce אינם תחליף ללקוח Web של האתר:
https://developers.google.com/identity/protocols/oauth2/resources/best-practices#manual_creation_and_configuration_of_oauth_clients

בוחרים OAuth client מסוג Web application ומשלימים את מסכי המותג/קהל/משתמשי הבדיקה הנדרשים בפרויקט. ב־Authorized JavaScript origins מעתיקים את המקור המדויק שהאשף מציג מתוך CMS_PUBLIC_ORIGIN. ביעד הזה הוא https://hichal.yoterberama.com — ללא /cms-api, ללא /admin וללא נתיב אחר. יש להשלים ב־Google כל אישור מקור או חשבון שנדרש; שדה בלוח המקומי אינו משנה את הרשאות הפרויקט.

מעתיקים לאשף Client ID בלבד. אין צורך ב־Client secret, סיסמת Google, הרשאות Cloud IAM חדשות או מפתח API חדש לאתר. גישה לפרויקט OAuth אינה מוכיחה בעלות באתר: החשבון שמשמש להוכחת הזהות צריך להתאים לבעל ההרשאה הקיים שאליו עוגן המנהל המקומי. אם אין גישה לחשבון הזה, משאירים את Google כבוי וממשיכים עם הכניסה המקומית; אין לשנות OWNERS כדי להעביר את הבדיקה.

5. הכנה, הוכחה והפעלה בלוח

בעל ההרשאה המקומי מזין Client ID וסיסמה מקומית נוכחית. פעולת הכנה שומרת מועמד נפרד ומנפיקה אתגר nonce התקף לחמש דקות, הקשור לסשן המקומי, למשתמש, לגרסת אישוריו ולבעלותו. שינוי מועמד אינו משנה את הלקוח הפעיל הקיים.

כפתור Google של האשף משתמש ב־Google Identity Services, initialize/renderButton, לקבלת ID token הכולל את ה־nonce. השרת מאמת חתימת RS256 באמצעות jose, את המנפיק, הקהל, הזמנים, ה־nonce ואת אימות הדוא״ל. הגיבוב של הזהות המאומתת חייב להתאים לעיגון הבעלים של החשבון המקומי. סשן אחר, הוכחה שפגה או חזרה על הוכחה שנצרכה אינם מאשרים את המועמד.

הוכחה מוצלחת עדיין אינה מפעילה Google. נדרשת לחיצה מפורשת על הפעלה ואימות נוסף של הסיסמה המקומית לפני תפוגת האתגר. השרת בודק שוב את הסשן ואת הגרסה תחת אותה נעילה ומפעיל את הלקוח בטרנזקציה. אם CMS_GOOGLE_AUTH_ENABLED=false, ההפעלה נדחית והלוח מסביר שנדרשת הגדרת האחסון. במקרה תפוגה או שינוי גרסה מתחילים בדיקה חדשה; אין לעקוף את שלבי ההוכחה.

הפעלת התצורה משאירה local_enabled=true ואינה מחליפה את ה־cookie המקומי. היא אינה כניסת Google רגילה ואינה אישור לבטל את הכניסה המקומית. לפני ביטול דרך הכניסה האחרונה נדרשת כניסת בעל הרשאה רגילה, עדכנית ומוצלחת דרך Google לאחר ההפעלה. אין חשבון או תפקיד חדש כתוצאה מהוכחת האשף.

שינוי הלקוח הפעיל מעלה גרסת מפתח של סשני Google המנוהלים ומבטל סשני Google קודמים; הסשנים המקומיים אינם משתנים. כשל בהוכחת מועמד אינו משבש את הלקוח הפעיל. סיסמאות ו־ID tokens נשארים בגוף בקשת HTTPS ובזיכרון הדרוש לבדיקה, ללא URL, מאגר או לוג; המשתמש מזין את הסיסמה בעצמו, לא בצ׳אט.

6. בדיקות יעד וחזרה לאחור

לפני הכרזה על חיבור תקין באחסון בודקים בפועל: local login עדיין עובד, מקור ה־JavaScript רשום נכון בפרויקט, הוכחת בעל הרשאה חיה מצליחה, activation מפורש מצליח, והתחברות Google רגילה מחזירה הרשאות צפויות. בודקים גם ש־Origin זר/CSRF חסר נדחים ושתוכן ופרסום עדיין חסומים במצב הקריאה בלבד. בדיקות RSA מקומיות, MySQL מבודד ודפדפן עם fixtures אינן מוכיחות הרשאה או זמינות בפרויקט Google האמיתי. בשלב כתיבת ההוראות אין טענה שאימות Google חי הושלם.

בכשל משאירים או מחזירים CMS_GOOGLE_AUTH_ENABLED=false, ושומרים CMS_LOCAL_AUTH_ENABLED=true ואת מצב הקריאה בלבד. לפני חזרה לקוד ישן ללא האשף יש לכבות את דגל Google במפורש ולתאם חסימת admin, כדי שלא תופעל בטעות תצורת Google הסטטית הישנה. מחזירים runtime וקובצי admin תואמים מגיבוי ובודקים כניסה מקומית; לא מוחקים את google_auth_config או את טבלאות auth ולא מריצים יבוא מחדש. סודות, מדיה, נתוני תוכן וגיבויים נשמרים. השינויים כאן אינם מפעילים CI/CD או מעבר סופי בין מסדי הנתונים.
