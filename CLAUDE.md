# היכל הקודש

Static Hebrew (RTL) site: `node scripts/build.mjs` turns `data/*.json` and `site/` into `dist/`.
Shared code is in `scripts/lib/` (core, layout, parts) and each part of the site has its own file in `scripts/lib/sections/`.
`npm run check` runs the unit tests in `test/` (`npm test`), ESLint, builds the site, checks every internal link and anchor, and audits the link structure (`scripts/audit-links.mjs --strict`: orphan pages and broken links fail; depth, generic anchors and link suggestions are only reported); it also runs on every pull request. `.github/workflows/link-audit.yml` runs the audit weekly and keeps the report in one open issue labelled `link-audit`. The editor's screen `#/links` ("קישורים ו־SEO") shows the audit of the last build (`admin/links.json`, written last by `scripts/lib/sections/links-audit.mjs`) and manages `data/link-audit.json` (`ignore`, `ignorePairs`, `aliases`, `related.count`/`related.exclude`; validated by `validateAuditConfig`, saved as a draft like any data file). Under each Q&A answer the build adds "שאלות קשורות" (`scripts/lib/related.mjs`, TF-IDF; `related.count` 0 turns it off). Alerts: the weekly workflow's issue and failed runs are emailed by GitHub to the repository's watchers; the site stores no email addresses. The library (`data/library.json`; `validateLibrary` in `core.mjs`): `series` group volumes into one card and a page `/library/<id>/` (optional `groups` split it, e.g. holidays and topics), `featured` is the "להתחיל כאן" row, `keywords` on a book or series are search words the library filter matches but the page does not show, and `occasions` (holidays, by Hebrew day and month, or a season by two parashot) give the seasonal suggestion on the library page and the home page: a month before the holiday its books are offered (`scripts/lib/seasonal.mjs`; the dates come from the Hebrew dates in `site/zmanim/`, made from the Onot app by `scripts/gen-zmanim.mjs`, so nothing is shown past that range; `site/app.js` picks the window of today's date; each occasion also has `icon`, `accent` (a colour from `ACCENTS` in `core.mjs`, classes `ac-<name>` in `site/css/13-seasons.css`), an optional `image` (a photo id from `data/images.json`) and `terms`, the holiday's names: every Q&A whose own title has one of them, up to 60, is that occasion's pool, written to `season/<id>.json`; the page shows three at random, unread first, and remembers what was read in the browser's localStorage `read:shut`, not in a cookie and not on the server). Rules for internal links (SEO/GEO): `.claude/skills/internal-links/SKILL.md`; a long list needs the numbered pager (`pagerHtml` in `parts.mjs`), not only previous/next.
When you change a helper in `scripts/lib/core.mjs` or `parts.mjs` that guards links or escaping, add or update its test.
Styles live in numbered parts in `site/css/`, joined in order into `dist/style.css`; put a rule in the part for its topic (order matters: later parts win).
The CSP has no `'unsafe-inline'` for styles: never write a `style="…"` attribute (the link check fails on one); use a class.
The tests need Node 24, the server's runtime (CI uses it). On an older Node about 24 server/runtime tests fail with "Node: version24 or newer is required"; that is the local environment, not a bug: run them with Node 24 (for example `npx -y node@24 --test test/*.test.mjs`).
`npm run lint` runs ESLint; a pre-commit hook (`.githooks/`, enabled by `npm run setup`) runs the tests and lint.
The live site is https://hichal.yoterberama.com/ (cPanel), published from the `claude/greeting-2i183o` branch; see "Publishing to cPanel" below. The old GitHub Pages site is retired.

## Working with another editor's branch (yaakov)

Yaakov, the other editor, publishes from the branch `yaakov`; the live site is built from `claude/greeting-2i183o`. Whatever either of them publishes is a commit, so it can be seen, but only after a fetch. Before ANY new write, upload or push, and again right before pushing:

1. `git fetch origin yaakov claude/greeting-2i183o`, then look at what is new (`git log HEAD..origin/yaakov`, `git diff HEAD...origin/yaakov --stat`) and which files both sides touched.
2. Merge both into your working branch (`git merge origin/yaakov`, `git merge origin/claude/greeting-2i183o`). Never overwrite, reset or force-push over their work: resolve so both sides' changes stay, and if both changed the same lines, stop and ask the user.
3. Run `npm run check`; it includes `npm run sync` (`scripts/check-sync.mjs`), which fails if either branch has commits yours lacks. The same check runs in the `pre-push` hook (`npm run setup` enables it) and on every pull request.

Editor publish never overwrites a live change silently: a draft is saved over the exact row it read (compare-and-swap in D1 and in MySQL), discard deletes only the rows it read (a newer save stays, reported as `kept`), the branch moves with `force: false`, and a file the live branch changed since the draft began is merged three ways (`cms-worker/json-merge.mjs`: base blob, live file, draft; fields and `id`-keyed list items; the same thing changed on both sides is a 409 conflict listed for a person, who can still `force`). Tests: `test/json-merge.test.mjs`, `test/worker.test.mjs`.

Not visible in git: editor drafts saved in D1 until someone publishes them. A publish conflict there needs a look at the difference, never a blind `force`. Do not force-push to `yaakov` or the live branch.

## Publishing to cPanel

A merge into `claude/greeting-2i183o` runs "Build cPanel release" (`.github/workflows/cpanel-release.yml`), which only builds a package; the runner installed on the host (`scripts/fast-cpanel-deploy.py`, private copy on the server) then publishes it.

- A green GitHub run is not proof of a deploy. After a merge, check that `/admin/build.json` shows the master commit and that `/admin/deployment.json` shows the same commit with `"state": "live"`.
- Merge a pull request only after its "Check site" run has passed: merging first makes the sync step fail against the PR's own merge commit.
- Package limits: at most 512MiB expanded, a package descriptor of at most 8MiB, and a download budget of at most 128MiB including the ZIP envelope. Use the checks in `scripts/package-cpanel-fast.mjs`; never remove them to make a build pass. A large addition (a book, many pages, PDFs) should be measured against them before merging.
- Files above 90MB belong in R2, not in the repository.
- If publishing is stuck: on the server, read `status.json` and `failure.json` in `/home/yoterber/heichal-cms/fast-deploy/` and diagnose by the actual error, without exposing secrets.
- A new file that the Node server imports must be included in the server package and in the allowed file list in `server/runtime-identity.mjs`.
- Changing the deploy runner in the repository does not update the private copy installed on the server; update that copy too, keeping a rollback copy.
- Keep Hebrew, RTL and the design system. Indexing stays blocked until an explicit decision to open the site.

## Editor (`/admin/`)

`site/admin/` is a static editor over `data/*.json`. With the editor server (`worker` in `site/admin/config.json`) a save is only a draft: it goes to D1 (`drafts` table, binding `DB`), never to GitHub, and the site does not change. Owners and editors marked as publishers ("מפרסם") publish chosen drafts from `#/changes`: one commit to the branch in `config.json` (written through the git data API, commit message with display names only, since the repository is public; emails stay in the D1 `log` table), and the Pages workflow then tests and publishes. Others only save drafts. A save over a file someone else saved meanwhile gets 409 (the editor keeps the typed text and offers to reload or overwrite); a draft whose live file changed since is flagged as a conflict at publish and needs `force`. Discard returns a file to the published state (editors only their own drafts), `history`/`restore` list commits of a file and bring one back as a draft, `/log` is the activity log (publishers; emails to owners only). Autosave: a copy in the browser every ~2 s (`cms-draft:<path>`, offered back after a crash) and a silent server draft after `autosaveSeconds` (default 30) idle, only when the form is valid. Editors set a display name on first sign-in (`/me`); owners set names and the publisher role in `#/editors` (KV key `people`). Without `worker` the editor asks for a personal GitHub token and every save is a direct commit.
Media (`#/media`, the page blocks image / video / audio / file, `MEDIA_EXT` and `validateCms` in `core.mjs`): the worker takes uploads in pieces and chooses the place by type and size, counting each free allowance (`MEDIA_GH_*`, `MEDIA_R2_*` in `wrangler.toml`; free-tier ceilings are the point, so keep them). Small files that are not video wait in D1 (`media`, `media_chunks`) as pending changes and are committed to `site/media/` in the publish commit (the build serves them as `/media/<file>`); large files and video go to the R2 bucket `heichal-media` (binding `MEDIA`), live at once, served by the worker at `/m/<file>` or by `MEDIA_PUBLIC_URL`. A page that points at `/media/<file>` is published only together with the file (the worker refuses otherwise, and `validateCms` fails the build for a missing file); the editor will not delete a file a page uses. Images need a description (alt); uploads are checked by their first bytes, and SVG/HTML are not accepted. When the site moves to its own domain, update `MEDIA_PUBLIC_URL`, the admin CSP (`img-src`/`media-src` in `site/admin/index.html`) and `ALLOWED_ORIGIN`.
Editors sign in with Google through `cms-worker/` (a Cloudflare Worker that checks the Google access token with Google, holds the GitHub token and only lets `data/` be written; setup in `cms-worker/README.md`, tests in `test/worker.test.mjs`, deployed by `.github/workflows/cms-worker.yml`). Owners are SHA-256 hashes of their emails in `OWNERS` (`wrangler.toml`; the repository is public, so no plain emails there); they add and remove editors from the editor itself, and that list lives in Cloudflare KV. While `worker` in `config.json` is empty, the editor asks for a personal GitHub token instead.
After a save the editor follows the publish: the site's deploy run for that commit (deploys are never cancelled midway; saves made meanwhile wait and only the newest is built) and then `admin/build.json`, which each build writes with its commit, so it says "on the site" only when the site serves it.
The editor's lists of pages and of Q&A come from the published `admin/pages/index.json` and `admin/shut/index.json`, which lag a save by a minute or two: which pages exist is asked from the repository itself, and what was just created, changed or hidden is kept in the browser (`cms-recent`, 15 minutes) and laid over the published list until it agrees.
It builds its forms from the shape of each JSON file, so a new field in a data file shows up without changing the editor; give a new field a Hebrew name in `LABELS` (and `TUPLES` for fixed-length rows) in `site/admin/admin.js`.
`data/shut.json` (25MB) is never rewritten by the editor: an edited, new or hidden Q&A entry is saved as `data/shut-edits/<id>.json`, which `mergeShut` in `core.mjs` applies over it (`validateShutEdit` fails the build on a bad one). The editor searches `dist/admin/shut/index.json` and reads entries from its chunks (`scripts/lib/sections/admin.mjs`).
Topics and new pages live in `data/topics.json` and `data/pages/<slug>.json` (blocks: text, cards, faq, quote, links, video, audio, file, and image and gallery, which name photos by id from `data/images.json`); `scripts/lib/sections/pages.mjs` builds them, and `validateCms` in `core.mjs` fails the build on a bad one.
A topic is a place in the site: `group` is the menu group it joins (the title of one of the site's own groups, or a new one; none means "נושאים נוספים"), and `kind` is `page` (a single page, like אומן: its one page is built at the topic's own address, and `validateCms` allows no second page) or `collection` (many items of one kind, like the library: optional `categories` `[{ id, title }]`, and a page names its own in `category`; `pages` is the old name of a collection and is still read as one). Either way a topic is one menu entry that links to its own address (the page itself, or the collection's list with a filter, chips and a section per category); a topic with no page is never shown. Moving a topic between groups, or changing its kind or categories, is done in the editor's topic settings.
The admin page has its own CSP (own scripts and styles only, no inline; Google's ready-made sign-in button needs inline styles, so the editor draws its own button and uses Google's token client); keep it strict.

## Photos

Photos are listed in `data/images.json` and live as ready sizes in `data/img/<id>/` (made by `node scripts/prepare-image.mjs`; the build itself uses no image library). The build fails on a missing or wrong-sized file, and on a page that shows a photo whose `rights` is not `approved`. Pages use the `image` and `gallery` blocks; `scripts/lib/images.mjs` writes them and `site/app.js` opens a gallery in a lightbox. The rules that a program can check are code and fail the build: `site/admin/image-rules.mjs` (alt text, credit, who else is in the photo and the written approval, gallery size, file budgets), shared with the editor, which must import it rather than copy it. The editor (`site/admin/admin.js`), the editor server (`cms-worker/worker.mjs`, which bundles that file) and `scripts/prepare-image.mjs` all import it, so a rule is changed in one place. The editor picks photos from the registry (`#/file/images.json` is the photo library), uploads a new one (it is made ready in the browser: sizes, thumbnails around the face, checks for width, lookalikes and edge bars) and cannot add, remove or resize one from a form; only the owner approves a photo or writes down who agreed to the people in it (`rights`, `consent`), and the server enforces that and checks again at publish, where a photo's files go out with its entry. `npm run e2e` (needs Playwright; it builds first) runs the editor against the real server code in a browser: `test/editor-audit.e2e.mjs` (every screen, phone, dark), `test/editor-photos.e2e.mjs`, `test/editor-upload.e2e.mjs`; the harness is `test/helpers/editor-world.mjs`. The rest (choosing, captions, children and groups) is in the `images` skill: `.claude/skills/images/SKILL.md`.

## Times of the year

`data/moadim.json` (`scripts/lib/moadim.mjs`, validated at build) lists the holidays in the order of the year: their book sections (`[slug, from, to]`), books, site links and the words that pick their Q&A. The build makes `/moadim/` and `/moadim/<id>/`, and links a section of a holiday to its hub from the reader. The home page's holiday band is not built from it (another branch, `ccr-d151216d-srvtyw`, builds a seasonal suggestion from `occasions` in `library.json`); once both are merged the two lists of holidays should become one. A book's `parts` in `data/library.json` are its table of contents (shown first on the book page; up to 80 sections open, more folded with a filter).

## Content that is missing or not ready

Never show visitors an empty or unfinished section. When something is not ready:

1. Hide it by adding its path to `hidden` in `data/site.json` (with a short `why`). The build then skips its
   pages, drops it from the menus and home tiles, and turns inline links to it into plain text.
2. Add an entry to `TODO.md` saying what is missing and what is needed to bring it back.

When the content arrives, remove the path from `hidden` and tick it off in `TODO.md`.
