# היכל הקודש

Static Hebrew (RTL) site: `node scripts/build.mjs` turns `data/*.json` and `site/` into `dist/`.
Shared code is in `scripts/lib/` (core, layout, parts) and each part of the site has its own file in `scripts/lib/sections/`.
`npm run check` runs the unit tests in `test/` (`npm test`), ESLint, builds the site, checks every internal link and anchor, and audits the link structure (`scripts/audit-links.mjs --strict`: orphan pages and broken links fail; depth, generic anchors and link suggestions are only reported); it also runs on every pull request. `.github/workflows/link-audit.yml` runs the audit weekly and keeps the report in one open issue labelled `link-audit`. The editor's screen `#/links` ("קישורים ו־SEO") shows the audit of the last build (`admin/links.json`, written last by `scripts/lib/sections/links-audit.mjs`) and manages `data/link-audit.json` (`ignore`, `ignorePairs`, `aliases`, `related.count`/`related.exclude`; validated by `validateAuditConfig`, saved as a draft like any data file). Under each Q&A answer the build adds "שאלות קשורות" (`scripts/lib/related.mjs`, TF-IDF; `related.count` 0 turns it off). Alerts: the weekly workflow's issue and failed runs are emailed by GitHub to the repository's watchers; the site stores no email addresses. Rules for internal links (SEO/GEO): `.claude/skills/internal-links/SKILL.md`; a long list needs the numbered pager (`pagerHtml` in `parts.mjs`), not only previous/next.
When you change a helper in `scripts/lib/core.mjs` or `parts.mjs` that guards links or escaping, add or update its test.
Styles live in numbered parts in `site/css/`, joined in order into `dist/style.css`; put a rule in the part for its topic (order matters: later parts win).
The CSP has no `'unsafe-inline'` for styles: never write a `style="…"` attribute (the link check fails on one); use a class.
`npm run lint` runs ESLint; a pre-commit hook (`.githooks/`, enabled by `npm run setup`) runs the tests and lint.
The live site is https://hichal.yoterberama.com/ on cPanel hosting (Apache for the static files, Node 24 through Passenger for the editor server, MySQL 8.4). It is published from the `claude/greeting-2i183o` branch: every push there runs `.github/workflows/cpanel-release.yml` (only while the repository variable `CPANEL_RELEASE_ENABLED` is `true`), which tests, builds the release with `scripts/package-cpanel.mjs` + `package-cpanel-fast.mjs` and keeps it as an Actions artifact; a private Cron on the host (`scripts/poll-cpanel-release.mjs`, `fast-cpanel-deploy.py`) downloads, verifies and swaps it in. Nothing is built on the host. Details and recovery: `docs/cpanel-publication.txt`, `docs/cpanel-route-guards.txt`, `server/README.md`. The release is still built as staging (`noindex` on every page and an `X-Robots-Tag` header); turning that off is a separate, deliberate step.
The old hosting no longer receives updates: `pages.yml` does not publish any more; it is a manual workflow that replaces the old GitHub Pages site with a redirect to the new address, and the Cloudflare Worker (`cms-worker/`, D1/KV/R2) is deployed only by hand and kept for rollback.

## Editor (`/admin/`)

`site/admin/` is a static editor over `data/*.json`, served at `/admin/`. Its server is `server/` (Node + MySQL on the host, API at `/cms-api`; the cPanel release writes that address into the editor's config, while `worker` in the repository's `site/admin/config.json` still names the old Worker). The server shares its data operations with `cms-worker/worker.mjs`: the Worker runs them on D1, Node on the MySQL adapters (`server/mysql-*.mjs`, schema in `server/mysql-*.sql`). A save is only a draft: it goes to the `drafts` table, never to GitHub, and the site does not change. Owners and editors marked as publishers ("מפרסם") publish chosen drafts from `#/changes`: one commit to the branch in `config.json` (written through the git data API, commit message with display names only, since the repository is public; emails stay in the D1 `log` table), and the Pages workflow then tests and publishes. Others only save drafts. A save over a file someone else saved meanwhile gets 409 (the editor keeps the typed text and offers to reload or overwrite); a draft whose live file changed since is flagged as a conflict at publish and needs `force`. Discard returns a file to the published state (editors only their own drafts), `history`/`restore` list commits of a file and bring one back as a draft, `/log` is the activity log (publishers; emails to owners only). Autosave: a copy in the browser every ~2 s (`cms-draft:<path>`, offered back after a crash) and a silent server draft after `autosaveSeconds` (default 30) idle, only when the form is valid. Editors set a display name on first sign-in (`/me`); owners set names and the publisher role in `#/editors` (KV key `people`). Without `worker` the editor asks for a personal GitHub token and every save is a direct commit.
Media (`#/media`, the page blocks image / video / audio / file, `MEDIA_EXT` and `validateCms` in `core.mjs`): the server takes uploads in pieces and chooses the place by type and size, counting each allowance (`MEDIA_GH_*`, `MEDIA_R2_*`: environment variables on the host, `wrangler.toml` on the legacy Worker; free-tier ceilings are the point, so keep them). Small files that are not video wait in D1 (`media`, `media_chunks`) as pending changes and are committed to `site/media/` in the publish commit (the build serves them as `/media/<file>`); large files and video are live at once: on the host they are kept in the private folder `CMS_MEDIA_ROOT` (`server/file-media.mjs`, outside the public root) and served by the server at `/m/<file>`; on the legacy Worker they went to the R2 bucket `heichal-media`. A page that points at `/media/<file>` is published only together with the file (the server refuses otherwise, and `validateCms` fails the build for a missing file); the editor will not delete a file a page uses. Images need a description (alt); uploads are checked by their first bytes, and SVG/HTML are not accepted. When the site's address changes, update the origins in `cpanel-release.yml` and the host scripts, `SITE_ORIGIN` in `check.yml`/`link-audit.yml`, the admin CSP (`img-src`/`media-src` in `site/admin/index.html`), `ALLOWED_ORIGIN`/`CMS_PUBLIC_ORIGIN` on the server and the Google client's allowed origins.
Editors sign in with Google, or, on Node only, with a user name and password (`CMS_LOCAL_AUTH_ENABLED`; `docs/local-auth.txt`, invitations `docs/local-invitations.txt`, Google setup wizard `docs/google-auth.txt`). Owners manage users and roles (administrator, editor, author, contributor, subscriber) in the editor; account emails go from help@hichal.yoterberama.com. The server holds the GitHub token and only lets `data/` be written; its settings are environment variables listed in `server/README.md`, never in the repository. The legacy Worker: `cms-worker/README.md`, tests in `test/worker.test.mjs`, manual deploy `.github/workflows/cms-worker.yml`. Owners are SHA-256 hashes of their emails in `OWNERS` (`wrangler.toml`; the repository is public, so no plain emails there); they add and remove editors from the editor itself, and that list lives in Cloudflare KV. While `worker` in `config.json` is empty, the editor asks for a personal GitHub token instead.
After a publish the editor follows the cPanel release for that commit and then `admin/build.json` (and `admin/deployment.json`, written by the host deployer), so it says "on the site" only when the site serves it.
The editor's lists of pages and of Q&A come from the published `admin/pages/index.json` and `admin/shut/index.json`, which lag a save by a minute or two: which pages exist is asked from the repository itself, and what was just created, changed or hidden is kept in the browser (`cms-recent`, 15 minutes) and laid over the published list until it agrees.
It builds its forms from the shape of each JSON file, so a new field in a data file shows up without changing the editor; give a new field a Hebrew name in `LABELS` (and `TUPLES` for fixed-length rows) in `site/admin/admin.js`.
`data/shut.json` (25MB) is never rewritten by the editor: an edited, new or hidden Q&A entry is saved as `data/shut-edits/<id>.json`, which `mergeShut` in `core.mjs` applies over it (`validateShutEdit` fails the build on a bad one). The editor searches `dist/admin/shut/index.json` and reads entries from its chunks (`scripts/lib/sections/admin.mjs`).
Topics and new pages live in `data/topics.json` and `data/pages/<slug>.json` (blocks: text, cards, faq, quote, links, video, audio, file, and image and gallery, which name photos by id from `data/images.json`); `scripts/lib/sections/pages.mjs` builds them, and `validateCms` in `core.mjs` fails the build on a bad one.
A topic is a place in the site: `group` is the menu group it joins (the title of one of the site's own groups, or a new one; none means "נושאים נוספים"), and `kind` is `page` (a single page, like אומן: its one page is built at the topic's own address, and `validateCms` allows no second page) or `collection` (many items of one kind, like the library: optional `categories` `[{ id, title }]`, and a page names its own in `category`; `pages` is the old name of a collection and is still read as one). Either way a topic is one menu entry that links to its own address (the page itself, or the collection's list with a filter, chips and a section per category); a topic with no page is never shown. Moving a topic between groups, or changing its kind or categories, is done in the editor's topic settings.
The admin page has its own CSP (own scripts and styles only, no inline; Google's ready-made sign-in button needs inline styles, so the editor draws its own button and uses Google's token client); keep it strict.

## Photos

Photos are listed in `data/images.json` and live as ready sizes in `data/img/<id>/` (made by `node scripts/prepare-image.mjs`; the build itself uses no image library). The build fails on a missing or wrong-sized file, and on a page that shows a photo whose `rights` is not `approved`. Pages use the `image` and `gallery` blocks; `scripts/lib/images.mjs` writes them and `site/app.js` opens a gallery in a lightbox. The rules that a program can check are code and fail the build: `site/admin/image-rules.mjs` (alt text, credit, who else is in the photo and the written approval, gallery size, file budgets), shared with the editor, which must import it rather than copy it. The editor (`site/admin/admin.js`), the editor server (`cms-worker/worker.mjs`, which bundles that file) and `scripts/prepare-image.mjs` all import it, so a rule is changed in one place. The editor picks photos from the registry (`#/file/images.json` is the photo library), uploads a new one (it is made ready in the browser: sizes, thumbnails around the face, checks for width, lookalikes and edge bars) and cannot add, remove or resize one from a form; only the owner approves a photo or writes down who agreed to the people in it (`rights`, `consent`), and the server enforces that and checks again at publish, where a photo's files go out with its entry. `npm run e2e` (needs Playwright; it builds first) runs the editor against the real server code in a browser: `test/editor-audit.e2e.mjs` (every screen, phone, dark), `test/editor-photos.e2e.mjs`, `test/editor-upload.e2e.mjs`; the harness is `test/helpers/editor-world.mjs`. The rest (choosing, captions, children and groups) is in the `images` skill: `.claude/skills/images/SKILL.md`.

## Content that is missing or not ready

Never show visitors an empty or unfinished section. When something is not ready:

1. Hide it by adding its path to `hidden` in `data/site.json` (with a short `why`). The build then skips its
   pages, drops it from the menus and home tiles, and turns inline links to it into plain text.
2. Add an entry to `TODO.md` saying what is missing and what is needed to bring it back.

When the content arrives, remove the path from `hidden` and tick it off in `TODO.md`.

## Site audits

Until the site moves to its own private domain, these issues are known and listed in `TODO.md` under
"עד המעבר לדומיין הפרטי": the site not yet having its own domain, the accessibility coordinator's details, the contact details, and the missing
anti-framing header (`frame-ancestors` / `X-Frame-Options`; `X-Content-Type-Options` is now sent by the release's `.htaccess`),
the long cache for versioned files (`_headers` is not read by Apache; it has to move into `.htaccess`), and the staging `noindex`.
An audit may mention them, but must not count them against any score or the overall grade.
