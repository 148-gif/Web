# הכנה ל־Node ו־MySQL ב־cPanel

לוח הניהול וה־API הקיימים נשמרים. הקבצים כאן מכינים את גבולות ההרצה והאחסון למעבר; **זו עדיין אינה חבילת שרת שאפשר לפרוס מול MySQL**. מנגנון הטיוטות והפרסום עדיין פונה ל־D1. לא בוצעו התקנה, חיבור למסד אמיתי או העברת נתוני ייצור.

ההכנה נבדקת על Node24. תמיכת Node באחסון כבר אומתה. יעד הסכימה הוא MySQL מודרני, 8.4 ומעלה; אין בכך אימות של גרסת האחסון בפועל. MariaDB אינו תחליף אוטומטי לסכימה הזאת, בפרט בגלל כללי ההשוואה של טקסט.

## הרכיבים המוכנים לבדיקה

- `http.mjs`: מתאם HTTP טבעי של Node סביב אותו Worker handler. הוא שומר על הזרמת בקשות ותשובות, ביטול חיבורים, שגיאות כלליות ו־CORS. הוא אינו פותח פורט בעצמו. `createCmsServer({env, publicOrigin})` מיועד למארח API נפרד, עם נתיבי `/session`, `/gh`, `/media` ו־`/m` הקיימים.
- `file-media.mjs`: `createFileMedia({root, maxBytes})` מספק את ממשק האחסון שה־Worker משתמש בו. מטא־נתונים ותוכן נשמרים יחד בקובץ מיכל, דרך קובץ זמני ו־rename אטומי. תיקיית השורש חייבת להיות פרטית, קנונית ומנוהלת בידי היישום, מחוץ לשורש האתר הציבורי. לא חושפים אותה ישירות ב־Apache. יש תוספת של 4KiB לקובץ שאינה נכללת במכסת המטען של ה־Worker. הנעילות המקומיות אינן מחליפות תיאום בין כמה תהליכי Node.
- `mysql-schema.sql`: סכימה מפורשת ליעד ריק בלבד. טקסט נשאר טקסט; collation מסוג `utf8mb4_0900_bin` משמר הבחנה באותיות וברווחים לצורך בדיקות גרסה. אין להריץ את קובץ הסכימה אוטומטית בבקשות API או על מסד קיים.
- `migration.mjs`: מאמת צילום נתונים ומייצר פעולות INSERT עם פרמטרים. הוא אינו מתחבר למסד ואינו מריץ SQL. היעדר טבלאות, כפילויות, מספרים שאינם מדויקים וחלקי קבצים לא תקינים נעצרים. העלאות ופעולות מחיקה פעילות נשמרות בתוכנית אך חוסמות מוכנות לייבוא.
- `readiness.mjs`: בדיקת דרישות מקומית, בלי הצגת ערכי סודות או פתיחת חיבור. גם כשהדרישות מוגדרות, `deploymentReady` נשאר false עד למימוש ולאימות השלבים החסרים.

## שימוש בכלי ההכנה

`npm run cms:preflight` בודק את סביבת ההרצה המקומית בלבד. קוד יציאה2 אומר שחסרות דרישות. הוא אינו בודק מרחוק את cPanel ואינו יוצר קבצים או משתמשים. משתני ההגדרה מפורטים בדוח לפי שמם בלבד; אין לשים סודות במאגר.

`npm run cms:plan -- --input /private/snapshot.json` מציג ספירות וחסמים בלבד. כדי לשמור תוכנית לביקורת מוסיפים `--out /private/new-plan-directory`. תיקיית הפלט חייבת להיות חדשה ומחוץ למאגר; ההרשאות הן0700 לתיקייה ו־0600 לקבצים. `manifest.json` נכתב אחרון וכולל גיבובי מקור, תוכנית וסכימה. קוד יציאה0 מציין שאין חסמי נתונים ידועים בצילום,2 מציין חסמים,1 מציין קלט לא תקין. אף קוד יציאה אינו מעיד שהמערכת מוכנה לפריסה. ברירת המחדל מגבילה את צילום הקלט ל־64MiB; יצוא גדול יותר דורש הכנת מסלול העברה מדורג ולא חיתוך נתונים.

פורמט צילום v1:

```json
{
  "format": "heichal-cms-snapshot",
  "version": 1,
  "tables": {
    "drafts": [],
    "log": [],
    "media": [],
    "media_chunks": [],
    "ai_usage": []
  },
  "kv": {}
}
```

המערכים בדוגמה ריקים לצורך הצגת הפורמט בלבד. בצילום אמיתי כל חמש הטבלאות חייבות להיות מלאות, וכל רשומה כוללת את כל עמודות המקור. `kv` כולל את כל המפתחות הקיימים מבין `people`, `editors`, `owner-names`, כאשר הערכים הם מחרוזות JSON מקוריות. צילום עקבי של D1 ו־KV מחייב עצירת כתיבות מתואמת; המאמת אינו יכול להוכיח שהיצוא היה עקבי. מוני `request_limits` הזמניים מתחילים ריקים במפורש. פורמט זה דוחה טבלת מקור לא מוכרת ואינו מוחק אותה בשקט.

אפשר לצרף `git: {repo, branch, commit}` כדי לתעד את גרסת המקור. קובצי האתר המפורסמים, תמונות וקבצים קטנים נשארים ב־Git. אובייקטי R2 הם תלות נפרדת ויש לבדוק ולהעתיק את הבתים והמטא־נתונים שלהם. אין להעתיק קובץ R2 גולמי ישירות לתיקיית המיכלים של מתאם הקבצים: יש להעבירו דרך `put` ולוודא גודל וגיבוב.

## השלבים שנותרו לפני העברה

1. לממש מתאם MySQL לפעולות הנתונים, לרבות השוואות אטומיות, החזרת מספרים מדויקים, נעילות מכסה וטרנזקציות. החלפה כללית של מחרוזות SQL אינה מספיקה. נדרש גם מתאם KV וטיפול אטומי במגבלות הקצב.
2. להוסיף דרייבר ולהריץ את הבדיקות מול MySQL אמיתי בסביבת בדיקה: חיבורים מקבילים, rollback, Unicode ורווחים, מגבלות packet וקריאה חוזרת זהה של צילום הנתונים. כרגע אין בסביבת העבודה mysql2 או שרת MySQL, ולא הותקנו רכיבים חדשים.
3. לתרגל העברת מסד וקבצים וגיבוי/שחזור. אין לשחרר רשומת R2 במצב `receiving` לאחר קריסה לפני בדיקה וניקוי של האובייקט שלה. קובצי `.upload-*` שנותרו אחרי קריסת Node דורשים ניקוי מתואם שאינו מוחק העלאה פעילה.
4. לאמת ב־cPanel את נתיב ההפעלה, כתובת ה־API, תשתית proxy אמינה, הרשאות אחסון, מגבלות זמן וקישוריות Google/GitHub. המתאם אינו סומך על כותרות forwarded שמגיעות מהלקוח; ללא הגדרת proxy מאומתת, משתמשים מאחורי אותו proxy עשויים לחלוק מכסת התחברות.
5. לעדכן בצורה מתואמת את `admin/config.json`, את כתובות ה־CSP ואת הגדרות Google. לשמר את כתובות המדיה הקיימות או לספק הפניות. להחליף את תהליך עדכון GitHub Pages בתהליך בנייה ופריסה מתאים ל־cPanel.
6. ההעברה תצא מהמסטר לאחר הכללת ההתאמות שנבדקו. `yaakov` נשאר ענף ההכנה והבדיקות. המיזוג למסטר מפעיל כיום אוטומטית פרסום ל־GitHub Pages ול־Cloudflare Worker; יש לבדוק גיבוי ויכולת חזרה לפני המיזוג, ולתאם את החלפת תהליך הפרסום כחלק מהמעבר.
