פרסום חוזר של האתר הציבורי ל־cPanel

המטרה היא שפרסום תוכן למסטר יגיע לאתר הבדיקה בלי העלאת קבצים דרך הדפדפן בכל פעם. GitHub Actions בונה חבילה מהקומיט המדויק, ותהליך Node פרטי באחסון מושך, מאמת ומפרסם את הקבצים הציבוריים. הבנייה אינה מתבצעת ב־cPanel: אין צורך להריץ שם Git, להתקין sharp או להחזיק תלויות פיתוח לצורך כל פרסום.

המסמך מתאר הכנה והפעלה מבוקרת. כתיבתו אינה יוצרת Cron, מפתח, מסד או פריסה. יעד הבדיקה הוא https://hichal.yoterberama.com/; מקור התוכן הוא המסטר המאושר, ששמו כעת claude/greeting-2i183o. ענף yaakov משמש להכנה ובדיקות.

1. גבולות המנגנון

מנגנון זה מפרסם קבצים ציבוריים בלבד. הוא אינו מעדכן את תהליך Node, מתקין תלויות, משנה משתני סביבה, מייבא מסד או מריץ שינויי סכימה. מדיה פרטית, סודות וגיבויים נשמרים מחוץ לשורש הציבורי ואינם נמחקים בהחלפת גרסה.

לכל חבילה יש מזהה קומיט, ענף, מקור אתר ומניפסט קבצים. גיבוב מניפסט היישום שבחבילה חייב להתאים ל־approvedRuntimeManifestSha256 שאושר מול גרסת השרת שהותקנה. שינוי בשרת מחייב עדכון נפרד ובדיקה לפני שמאשרים גיבוב חדש. אין לאשר אוטומטית את הגיבוב של החבילה הבאה כדי לעקוף חסם.

האתר הציבורי נשאר עם noindex. לוח הניהול נשאר חסום באמצעות admin/.htaccess כל עוד חיבור ה־CMS לא הושלם. תהליך הפרסום משמר את החסימה; הוא אינו פותח את הלוח מעצמו.

2. הבנייה ב־GitHub

קובץ התהליך הוא .github/workflows/cpanel-release.yml. הוא מופעל רק כאשר משתנה המאגר CPANEL_RELEASE_ENABLED שווה בדיוק למחרוזת true. עד להשלמת ההגדרות והבדיקות משאירים אותו כבוי. הפעלת משתנה זה מאפשרת בניית חבילות; היא אינה מפעילה את ה־Cron באחסון ואינה מסירה את הגנות הפרסום.

הבנייה משתמשת במקור המאושר מהמסטר ובתלויות הנעולות. הרשאת ה־workflow היא contents: read; הרשאת Actions לקריאה נדרשת בנפרד לטוקן של ה־runner באחסון. העלאת התוצר משתמשת ב־upload-artifact מקובע. אין צורך לתת לתהליך הבנייה סודות cPanel או סודות מסד. החבילה אינה מכילה צילום מסד, סודות או את קובץ .htaccess החי של האחסון.

ה־runner באחסון בודק את ראש המסטר, מאתר הרצה מוצלחת של cpanel-release.yml עבור אותו SHA ומוריד את התוצר המתאים. עצם קיומו של ZIP או שם קובץ מתאים אינם מספיקים. לפני החלפת הקבצים נבדק שוב שהמקור לא התקדם. תוצר ישן אינו מחליף גרסה חדשה יותר.

אם יש כבר workflow של GitHub Pages או Cloudflare Worker, הוא נשאר תהליך נפרד. הצלחה באחד מהם אינה הוכחה שהפרסום ל־cPanel הצליח.

3. התקנה ראשונית באחסון

ב־cPanel נצפו File Manager, Git Version Control, Setup Node.js App ו־Cron Jobs. Terminal לא אומת. ניתן להתקין את ה־runner פעם אחת דרך File Manager בתיקייה פרטית. Git Version Control הוא אפשרות לקבלת עותק קוד פרטי ראשוני; אין צורך להפעיל Git בכל פרסום.

ה־runner משתמש ב־Node ובמודולים המובנים בו. אין צורך להתקין unzip או תלויות חילוץ. מפעילים קובץ קבוע שנבדק, לא סקריפט שהורד מתוך חבילת הפרסום. עדכון ה־runner עצמו הוא פעולה נפרדת מעדכון האתר.

חלוקת תיקיות מוצעת:
קוד ה־runner: /home/yoterber/heichal-cms/publication-runner
תצורה פרטית: /home/yoterber/heichal-cms/publication/config.json
מצב, מועמדים וגיבויים: /home/yoterber/heichal-cms/publication-state
קובץ הרשאה פרטי: /home/yoterber/heichal-cms/secrets/github-actions-token
שורש האתר שאומת: /home/yoterber/hichal.yoterberama.com

אלה נתיבים מוצעים, מלבד שורש האתר שכבר אומת. יש ליצור ולאמת אותם לפני שימוש. תיקיות פרטיות בהרשאות 0700 וקובצי תצורה והרשאה בהרשאות 0600, בבעלות המשתמש שמריץ את התהליך. אין symlinks ואין להציב stateRoot בתוך האתר, בתוך תיקיית קוד מתחלפת או בתוך מאגר המדיה הפרטית. קובץ התצורה וקובץ ההרשאה חייבים להיות מחוץ ל־stateRoot ולשורש הציבורי.

את הנתיב המוחלט ל־Node לוקחים מההגדרה בפועל ב־Setup Node.js App ובודקים בהרצת הכנה. אין להניח ש־node שב־PATH של Cron הוא Node 24.22.1 שנבחר לאפליקציה. Cron אינו יורש בהכרח את משתני הסביבה של Node Selector.

4. הרשאה ותצורה

משתמשים בהרשאה קיימת ומאושרת למאגר 148-gif/Web, עם גישת Actions לקריאת תוצרים. אם משתמשים ב־GITHUB_TOKEN הקיים של השרת, יש לוודא שהרשאה זו קיימת בפועל; עצם הצלחת קריאת הקוד אינה מוכיחה שאפשר להוריד תוצרי Actions. ההכנה אינה יוצרת טוקן או משנה הרשאות.

הערך נשמר בקובץ הפרטי שמזוהה ב־githubTokenFile. אין להכניס אותו לתצורת JSON, לפקודת Cron, ל־URL, ללוג או למאגר. אין להדפיס את תוכן הקובץ לצורך בדיקה. הנתיב עצמו אינו סוד.

שדות התצורה:
version: המספר 1.
enabled: ערך boolean. מתחילים ב־false; מפעילים רק לאחר השלמת ההכנה. זהו שער נוסף, נפרד ממשתנה הבנייה ב־GitHub ומדגל --apply.
repo: הערך 148-gif/Web.
branch: שם המסטר שאומת במאגר; כעת claude/greeting-2i183o.
siteOrigin: הערך https://hichal.yoterberama.com, ללא נתיב.
documentRoot: הערך /home/yoterber/hichal.yoterberama.com.
stateRoot: תיקיית המצב הפרטית והמבודדת.
githubTokenFile: נתיב מוחלט לקובץ ההרשאה הפרטי.
approvedHostConfigSha256: SHA256 של קובץ .htaccess החי, לאחר שילוב ובדיקה של הוראות התחזוקה.
approvedRuntimeManifestSha256: גיבוב מניפסט היישום שתואם לגרסת שרת ה־CMS שנבדקה והותקנה.
probePaths: מערך נתיבים ציבוריים לבדיקת HTTP לאחר החלפת הקבצים; למשל /, /style.css ו־/media/843c14df-28-10-26-1.pdf.

יש להשתמש בגיבובים שנמדדו ואומתו, לא במחרוזות דוגמה. גיבוב קובץ ZIP, גיבוב מניפסט היישום ו־SHA של קומיט הם מזהים שונים ואין להחליף ביניהם. אם cPanel שינה את .htaccess מאז אישורו, בודקים את ההבדל לפני אישור גיבוב חדש.

פורמט התצורה מאפשר null בשדות הגיבוב לצורך הכנה בלבד. החלה דורשת enabled=true ושני גיבובי SHA256 תקינים. כאשר גיבוב .htaccess עדיין null, ה־dry-run מוריד ומאמת את התוצר ומחזיר state=blocked עם הסיבה approve-host-configuration-before-full-dry-run, לצד requiredHostConfigSha256 ו־requiredRuntimeManifestSha256. אלה ערכים לבדיקה, לא אישור אוטומטי: תחילה משלבים ובודקים את בלוק התחזוקה ומאמתים את גרסת השרת. רק לאחר מכן מאשרים את הגיבובים ומריצים תכנון החלפה מלא. requiredRuntimeManifestSha256 מחושב על JSON.stringify של רשומות app/ מהמניפסט, ממוינות לפי path, כשבכל רשומה path, bytes ו־sha256.

5. הכנת .htaccess וחלון התחזוקה

מנגנון ההחלפה דורש ב־.htaccess החי את בלוק התחזוקה המדויק שמיוצא כ־CPANEL_MAINTENANCE_RULES מתוך server/cpanel-release.mjs. משלבים את הבלוק אחרי קריאת התצורה החיה ושמירת גיבוי, תוך שימור הוראות PHP, Passenger ו־noindex. אין להחליף את הקובץ החי בקובץ מתוך חבילת האתר ואין לנסח גרסה דומה של הבלוק בלי לבדוק את התאמתה למנגנון.

לאחר השילוב בודקים בפועל mod_rewrite ו־mod_headers ואת התגובה לשער התחזוקה, ואז שומרים את גיבוב הקובץ ב־approvedHostConfigSha256. נוכחות הטקסט בקובץ אינה מוכיחה שהשרת מפעיל את ההוראות.

בזמן החלפת הקבצים נוצר בשורש הציבורי הדגל .cpanel-maintenance, המשויך למזהה הפרסום. הבלוק מחזיר 503 בזמן ההחלפה. זהו חלון תחזוקה מפורש: החלפה של אלפי קבצים אינה הופכת לאטומית רק משום שכל קובץ מועבר באמצעות rename.

לאחר השלמת כל הקבצים מסירים את הדגל במסגרת התהליך, מבצעים בדיקות HTTP ומאמתים את סמן הקומיט. רק אחרי שהבדיקות עוברות מדווחים שהגרסה חיה. כשל או קריסה במהלך החלפה עלולים להשאיר את דגל התחזוקה. אין למחוק אותו ידנית כדי להציג אתר שחלק מקבציו עדיין מגרסה אחרת.

6. מחזור פרסום

א. קוראים תצורה ומאמתים נתיבים, הרשאות, מקור וגיבובים מאושרים. מצב כבוי אינו אישור לפרסום.
ב. תופסים נעילה פרטית. אם כבר פועל פרסום, אין להתחיל פרסום נוסף ואין לשבור את הנעילה לפי גיל בלבד.
ג. בוחרים תוצר מוצלח המתאים לראש המסטר, מורידים אותו ומאמתים את גיבוב התוצר. החילוץ מוגבל בגודל ובמספר קבצים ודוחה נתיבים חורגים ו־symlinks.
ד. משחזרים מועמד בתיקייה פרטית, משווים כל קובץ למניפסט ובודקים מקור, קומיט והתאמה לגרסת השרת המאושרת.
ה. מוודאים שוב את ראש המסטר, את .htaccess החי ואת היעדר שינוי מקביל. שומרים יומן וגיבוי לפני שינוי באתר.
ו. מפעילים את שער התחזוקה ומחליפים רק קבצים שמנוהלים על ידי המנגנון. אין סנכרון שמוחק את כל מה שחסר בחבילה.
ז. לאחר השלמת ההחלפה מסירים את השער, בודקים את נתיבי probePaths ואת סמן הבנייה ורושמים הצלחה רק אם הבדיקות עברו.

הנתיבים הבאים נשמרים: .htaccess בשורש, admin/.htaccess, .well-known, cgi-bin, php.ini, .user.ini ו־admin/deployment.json. קובץ הסטטוס מנוהל בנפרד מקובצי התוכן. קבצים מוגנים אינם נדרסים רק משום שהם מופיעים ב־ZIP.

אם האתר הסטטי כבר קיים לפני התקנת המנגנון, נדרש אימוץ ראשוני מפורש של הקבצים לאחר גיבוי ובדיקת המניפסט, באמצעות --adopt-existing. בודקים תחילה עם הדגל ב־dry-run, ורק לאחר בדיקת התוצאה מחילים אותו פעם אחת עם --apply. אין להניח שכל קובץ קיים שייך למנגנון או למחוק אותו. ההרשאה לאימוץ ראשוני אינה נכנסת לפקודת Cron קבועה.

7. פקודות בדיקה והפעלה

מתיקיית הקוד הפרטית, בסביבת Node המאומתת:
node scripts/publish-cpanel.mjs --config /home/yoterber/heichal-cms/publication/config.json

ברירת המחדל היא dry-run. היא אינה מחליפה את קובצי האתר. בדיקה שמורידה ומאמתת תוצר עדיין עשויה להשתמש ברשת ובתיקיית המצב הפרטית; אין לפרש אותה כהבטחה לאפס קריאות או אפס קבצים זמניים.

אפשר לציין --dry-run במפורש; אין לשלב אותו עם --apply. אם פרסום נכשל או חזרה לאחור חסמה את הקומיט שנכשל, ניסיון חוזר לאותו קומיט דורש --retry-failed לאחר בירור הסיבה. אין להוסיף דגל זה לפקודת Cron קבועה.

החלפת האתר מחייבת במפורש:
node scripts/publish-cpanel.mjs --config /home/yoterber/heichal-cms/publication/config.json --apply

רק לאחר בדיקת התהליך באחסון אפשר להגדיר Cron עם נתיב Node מוחלט, נתיב מוחלט לסקריפט ונתיב התצורה. אין להעתיק את המילה node לדוגמת Cron בלי לבדוק PATH. אין ליצור Cron במהלך ההכנה. פלט תפעולי נשמר בתיקייה פרטית, עם סבב לוגים מוגבל; אין לפרסם אותו באתר.

תדירות Cron צריכה להתאים למשך ההורדה וההחלפה. החבילה שנבדקה הייתה כ־226MB, ולכן מדובר בפעולה שעלולה לקחת דקות. הנעילה חייבת למנוע חפיפה, וגם כשאין גרסה חדשה אין להוריד ולפרסם מחדש את אותו SHA.

8. מצב פרסום בלוח

admin/deployment.json הוא מסמך סטטוס ציבורי מצומצם למעקב אחר cPanel. הוא כולל רק מידע שנועד להצגה, כגון מצב התהליך, SHA וזמן. אין לכתוב בו נתיבים פרטיים, סודות, תשובות GitHub גולמיות או שגיאות פנימיות.

הגדרת המעקב בלוח נכללת בחבילת cPanel בלבד. הצלחת הבנייה ב־GitHub אינה מספיקה להצגת הצלחה בלוח: נדרשים סיום ההחלפה, התאמת סמן הבנייה ובדיקות HTTP. לפני הפעלת הפרסום יש לוודא ש־BRANCH בצד השרת, הענף ב־admin/config.json ומקור הבנייה מצביעים לאותו מסטר מאושר.

כאשר /admin/ חסום בכוונה, גם קובצי הסטטוס והסמן שבו אינם נגישים לציבור. בדיקת ההחלה הנוכחית דורשת קריאה מוצלחת של /admin/build.json, ולכן אין להפעיל עדיין את הפרסום האוטומטי במצב זה. אין להסיר את חסימת הלוח רק כדי לגרום לבדיקה להצליח; משלימים קודם את שלב ה־CMS ואת פתיחת הלוח המבוקרת, או משלימים בנפרד מסלול אימות מתאים לשלב הסטטי. אין להכריז על הצלחת אימות HTTP של סמן חסום.

9. שחזור וטיפול בתהליך שנקטע

בתיקיית stateRoot נשמרים runner.lock/owner.json לנעילת ה־runner, lock/owner.json לנעילת ההחלפה, pending.json, current.json, publication.json ותיקיות releases/<RELEASE_ID> עם journal.json וגיבויים. מזהה שחזור הוא מזהה פרסום שנמצא במצב המקומי, לא SHA שנבחר באופן שרירותי.

בדיקת שחזור ללא החלה:
node scripts/publish-cpanel.mjs --config /home/yoterber/heichal-cms/publication/config.json --rollback RELEASE_ID

החלת השחזור דורשת גם --apply. טיפול מפורש בתהליך שנקטע משתמש ב־--rollback RELEASE_ID --recover, וגם בו שינוי הקבצים דורש --apply. אין להוסיף --recover ל־Cron רגיל או להשתמש בו בלי מזהה שחזור. אין לשלב שחזור עם --adopt-existing או --retry-failed. שחזור צריך לשמר את התצורה והקבצים המוגנים ולבדוק את האתר לאחר ההחזרה. אם בעל הנעילה עדיין רץ, recovery אינו רשאי להשתלט עליו.

אין למחוק ידנית lock, pending או גיבוי כדי לעקוף חסם. במקרה לא ברור שומרים את שער התחזוקה ואת הראיות, בודקים את מצב הקבצים והיומן, ורק אז מבצעים שחזור מפורש. מסד הנתונים והמדיה הפרטית אינם משוחזרים כחלק מפקודת שחזור סטטית.

שומרים מספר מוגבל של גרסאות מאומתות בהתאם למכסת הדיסק וה־inodes, עם מקום גם להורדה, לחילוץ, לגיבוי ולעותק המוכן להחלפה. ה־runner עוצר לפני פרסום נוסף כאשר קיימות כבר חמש תיקיות פרסום שמורות, ודורש לפחות 2GiB פנויים במערכת הקבצים. בדיקת מערכת הקבצים אינה מוכיחה שיש מקום במכסת חשבון cPanel; גם אותה צריך לבדוק.

אין מחיקה אוטומטית של גיבויים כדי לפנות מקום לפרסום חדש. בהגעה למגבלה מארכבים גרסאות ישנות באופן מבוקר, תוך שימור המניפסט שעליו מצביע current.json ושרשרת השחזור הנדרשת. אין למחוק גיבוי שמשמש פרסום פעיל או שחזור. לתוצרי Actions יש תוקף; ב־workflow הנוכחי retention-days הוא 14. חזרה לאחור צריכה להתבסס על העותק המקומי שנשמר ולא על קישור ישן שעלול לפוג.

10. מה עדיין צריך לבדוק באחסון

הנתיב המדויק ל־Node של Cron; גישה יוצאת ב־HTTPS ל־GitHub ולהורדות התוצרים; מגבלות זמן, נפח הורדה ודיסק; הרשאות הקבצים; פעולת mod_rewrite ו־mod_headers; התנהגות 503 ו־noindex בזמן תחזוקה; והשחזור לאחר כשל מבוקר. זמינות Node 24.22.1 ו־MySQL 8.4.11-cll-lve כבר אומתה, ואין צורך לבקש שוב הוכחה לזמינותם.

הפעלת CMS מלאה עדיין תלויה ב־Passenger וניתוב /cms-api באחסון, כניסת Google מהמקור הנכון, הרשאות GitHub, מסד מאומת וייבוא הנתונים. יכולת Workers AI מטופלת בנפרד. תהליך הפרסום המתואר כאן אינו משלים יכולות אלה מעצמו.

לאחר העלאת שינויי המקור, מעבר הבדיקות ומיזוג מאושר, חבילת המעבר הסופית נבנית מה־SHA המדויק של המסטר. אין לשנות ידנית את סמן הקומיט כדי לייחס חבילה ישנה לקומיט חדש.
